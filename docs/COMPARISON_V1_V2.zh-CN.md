# V1/V2 同预算对照：2026-10-27

本轮问题：在相同费用、时间和设备可用条件下，两个完整系统在 Wine Quality 上的表现如何。
这是系统级比较，V2 同时拥有更自由的模型空间和新的内部早停组件，不能把差异单独归因于代码生成或早停。

## 启动前冻结的规则

- 数据：现有 Wine Quality 三分类任务，保持既有清洗与划分方法。
- 种子：17、42、73；每个种子的 V1/V2 使用完全相同的数据与划分。
- V1 为 `agent`，V2 为 `codegen`；DeepSeek 模型与价格快照、最大输出 token 相同。
- 每次估算 API 费用上限 1 元，共六次，配置费用上限合计 6 元。
- 每次配置运行时限 600 秒，单次训练及最终重训时限均为 120 秒；搜索为最终重训预留时间。
- 每次最多 100 个候选，仅作为安全上限。允许 Agent 提前停止，V1 的有限空间也可能耗尽。
- 两边均使用 `device: auto`，允许同一台机器的 CPU/GPU；配置 4 个训练工作线程。
- V2 有 Docker 的 4 CPU／8GB 主机内存硬限制，V1 使用原有线程约束，不声称两边内存隔离完全相同。
- 六次串行运行，期间不启动其他训练或测试；seed 42 反转执行顺序，减少固定先后顺序的影响。
- 以验证 macro-F1 选择模型，再最终评估测试集；不依据已完成的测试分数修改后续配置。
- 运行统计同时记录程序内部计时与完整调用墙钟耗时，后者包含前置检测、导出等开销。
  前置检测和清理开销可能使完整墙钟时间超过配置时限。
- 原样保留无效方案、失败候选、提前停止和 partial 状态。未知 API 用量会停止整个 suite。

Wine Quality 已用于开发，本轮属于单任务的描述性比较。三个种子不支持普遍优势或统计显著性结论。
需要独立评估早停贡献时另做开关消融；新任务上的泛化结论需要未参与开发的数据。
