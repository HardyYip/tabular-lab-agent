# 下一次一起读代码：看懂一个真实 Agent 闭环

这次不重新学习训练/验证/测试概念，也不先猜参数。先用约 20 分钟跟踪一条实际决策链。

## 本次材料

- `examples/live-v2/demo/experiments.json`：两段生成代码失败，第三段成功。
- `examples/live-v2/demo/candidate.py.txt`：最终选中的真实生成代码。
- `examples/live-v2/README.md`：实际结果和已确认的错误根因。
- `tabular_lab/runner.py`：`run_task()`、`pending_code`、`repair_count`、`best`。
- `tabular_lab/llm.py`：`CodePlan`、`JSONClient.ask()`、`code_prompt()`。
- `tabular_lab/sandbox.py`：`evaluate_code()`、`docker_command()`、`finalize_code()`。

本机完整上下文在 `runs/20261026T133749Z-0f212fa3/events.jsonl`，不必上传聊天或 GitHub。

## 第一步：画出一次状态变化

一起定位“候选失败后”的几行代码，标出上一段代码、错误信息、修复次数如何进入下一次请求。
由导师提供一个请求上下文的精简版本，用户根据真实代码指出哪些字段是 Agent 的输入，
哪些状态由执行器保存。这里重点是 Agent 的记忆和控制流怎样落到普通 Python 数据结构中。

## 第二步：看最终代码如何接入执行器

只读 `build_pipeline()` 的预处理与模型组合，追踪谁调用 `fit()`、谁评分、谁保存模型。
结合实际挂载目录，解释为什么生成代码不能自行决定得分，为什么部署预测不需要 LLM。

## 第三步：判断一次“修复成功”能说明什么

比较旧 CatBoost 候选与最后的随机森林组合。确认模型换了算法，不等于修复了原始错误。
再看只读根目录和可写临时目录的对照结果，理解什么时候应修执行环境，什么时候应改生成代码。

## 用户参与的小任务

由导师给出两个已经整理好的上下文样例，一个有错误反馈、一个只有分数。
用户说明自己希望下一轮 Agent 优先解决什么，再共同决定是否需要调整反馈字段。
不要求凭空发明算法；若决定改动，只做一个小改动，并比较改动前后的实际请求。

本次结束时，应能解释“规划器提出什么、执行器掌管什么、分类模型学习什么”，
并独立追踪一次提案 → 执行 → 反馈 → 新提案的调用关系。之后再进入四数据集对照结果分析。
