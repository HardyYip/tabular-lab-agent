# 扩展交付与学习路线

本轮把三个方向做成了可运行、可验证的实现：安全恢复实验、生产 HTTP 总截止，以及离线多模态分类。
没有恢复付费模型 API，也没有重跑旧 V1/V2 benchmark。原始比较仍是两次 partial 和一次未知用量。

## 已交付能力

| 能力 | 实现 | 验证范围 |
| --- | --- | --- |
| benchmark 恢复 | 协议、输入指纹、镜像 ID、文件锁、原子检查点、dry-run | 中断、孤立结果、并发、变化、未知用量均有测试 |
| HTTP 总截止 | 独立请求进程、超时终止、1 MB 响应上限、未知用量停止 | 真实本机慢响应服务，不调用外部 API |
| 图像分类 | 受限本机图片读取、409 维默认固定描述 | 图形数据训练、导出、新进程预测及 Docker 路径 |
| 文本／混合输入 | 无词表拟合的字符哈希，和图像／表格特征组合 | 中英文文本、缺失、资源限制、划分及预测一致性 |
| 兼容旧模型 | 原格式缺少模态字段时保留旧预测路径 | 两份真实旧导出各 1,064 行完全一致 |

本机分两组通过：125 项离线、11 项实际 Docker，后者含 2 项 GPU，共 136 个互不重复测试，无跳过。
静态检查通过。两轮合成演示分别完成 2／4 个候选，API 调用均为 0；测试 macro-F1 均为 1.0，
各验证了 12 条新进程预测。合成样例的简单性决定这些分数只能用于功能验收。

新 worker 已设为本机默认，两个历史 worker 均保留；旧模型仍使用原来的不可变 image ID。
机器可读证据与原始演示只留在被 Git 忽略的 runs/ 和 data/，不进入公开仓库。

## 明确的能力边界

- 这是有标签的分类入口，图像特征没有预训练语义；不提供任意图文对话、OCR 或目标检测。
- 同一图片像素的重复会参与外层分组，不识别近似照片；subject 分组也不代表 helper 内部监控已具备主体分组。
- 总 HTTP 截止能终止本机请求进程，不能证明服务端停止计费；未知用量仍不重试。
- 只有最终 summary 完整且协议一致的运行能恢复；中途可能收费的未完成运行不自动重发。
- 真实 LLM 的新版本效果尚未验证，余下四次旧比较没有被新版本冒充补齐。

## 从哪里开始读

1. 先按 [多模态指南](MULTIMODAL.zh-CN.md) 运行 image-demo，再用 inspect 看原始列如何变成 409 维特征。
2. 对照 features.encode_features 和 models.build_pipeline：前者无拟合状态，后者的填补、缩放和模型必须只在训练中拟合。
3. 读 [恢复指南](BENCHMARK_RESUME.zh-CN.md)，理解为什么“同一个 seed”不足以证明是在继续同一个实验。
4. 读 [请求计时](REQUEST_TIMING.zh-CN.md) 与 tests/test_http_request.py，区分阶段 timeout、总截止和费用未知。
5. 最后看 tests/test_multimodal.py 的 Docker 分支：生成代码只拿编码特征，宿主始终不加载生成模型。

PowerShell、仓库根目录下可以先做完全只读的计划检查：

```powershell
.\.venv\Scripts\python.exe -m tabular_lab benchmark --suite configs/benchmark-v1-v2.yaml --dry-run
```

它不训练、不创建 benchmark 结果、不读取密钥。当前配置的费用上限是快照，不是账单或余额核验。
完整分阶段验证与 CI 链接见 [验证状态](VALIDATION.md)。
